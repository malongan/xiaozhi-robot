# 2026-10-26 版本说明（r3）：启动快 2.7 倍 + 界面跟手

本版只做性能优化，**功能与 r2 完全一致**：启动从 14.4 秒降到 5.4 秒，
界面在音频忙时不再卡顿。没有任何功能增删，也没有改分区表与 NVS 布局。

- 基线：`custom-final-20261026-r2`（提交 `d43a5f7`）

## 一、如何退回上一版（r2）

本版**只改 app 分区**，回退同样是写一个地址，NVS / Wi-Fi 凭据 / 蓝牙配对 /
音乐索引 / 聊天记录全部保留：

```bash
# 退回 r2（从 GitHub Release 下载 r2 的固件）
python -m esptool --chip esp32s3 -p /dev/cu.usbmodem31101 -b 460800 \
  --before default-reset --after hard-reset write-flash 0x20000 xiaozhi-r2.bin
```

源码层面回退：把 `main` 重置到本版之前即可，`d43a5f7` 就是 r2 的确切状态。

```bash
git reset --hard d43a5f7   # 或 git revert 以下三项提交
```

本版新增的三个提交：

| 提交 | 内容 | 单独回退影响 |
|---|---|---|
| `5f18011` | OTA 后台化 + SD 40 MHz + LVGL 40 行 + CRC 查表 | 启动变慢回 14.4 s |
| `abca6bb` | 修 OTA 对象生命周期（上面那项的连带修复） | **必须与上一项一起回退** |
| `75dfebc` | LVGL 优先级 1 → 2 | 界面回到卡顿状态 |

> `abca6bb` 修的是 `5f18011` 引入的崩溃，两者不可分开回退。

## 二、本版改动

### 2.1 启动不再等版本检查（收益最大）

**问题**：`CheckVersion()` 只有一次 HTTP，实测建连 4.86 秒，却卡在协议初始化
之前，设备要等它才可用。

**关键发现**：这次检查下发的 `mqtt` / `websocket` 配置**早已写进 NVS**
（`settings.SetString`），所以重启时没必要等它。

**做法**：有缓存就用缓存先建链、立刻报可用，版本检查交给独立任务在后台完成。
首次开机（NVS 无缓存）与未激活设备仍走原来的阻塞流程——激活码要显示给用户，
那种场景必须等服务器响应。

### 2.2 SD 卡 20 → 40 MHz

`SDMMC_FREQ_DEFAULT`（20 MHz）→ `SDMMC_FREQ_HIGHSPEED`（40 MHz）。
词库加载、音乐读取、聊天记录写入的 I/O 带宽翻倍。

### 2.3 LVGL 绘制缓冲 24 → 40 行

单缓冲从 11 KB 增至 19 KB（双缓冲 22 → 38 KB），刷长回复和翻页更顺。
代价是 15 KB 内部 RAM。

### 2.4 LVGL 任务优先级 1 → 2

原来是系统最低档（1），低于 `opus_codec`(2)、`audio_output`(4)、
`audio_input`(8)，音频一忙 UI 就被饿死，点击和翻页不跟手。

**为什么不是 3**：先按清单建议试了 3，实测出现上行编码丢帧：

```
W AudioService: Encode queue is full, dropping oldest frame (dropped 2 so far)
```

批次 A 的日志里这一条是 0 次，说明 3 确实抢了编码任务的 CPU。降到 2 后
（与 `opus_codec` 持平、低于 `audio_output`）8 轮对话实测 0 丢帧。

### 2.5 聊天记录 CRC16 改查表

`ChatLog` 的 CRC 原来按位循环（每字节 8 次），改成查表（每字节 1 次）。
**结果与逐位版本逐字节一致**（含全部 256 种字节取值），磁盘格式不变，
已有记录照常校验通过。

## 三、实测结果

### 3.1 启动

| 指标 | r2 | r3 | 变化 |
|---|---|---|---|
| 启动到可用（`Activation done`） | 14.4 s | **5.36 s** | **−9.0 s（快 2.7 倍）** |

日志佐证版本检查确实挪到了后台：

```
I (5360) Application: Activation done          ← 已可用
W (4441) Application: 有缓存配置，先建链，版本检查转后台
I (5791) Ota: Current version: 2.5.2           ← 后台才开始检查
I (6441) HttpClient: ... api.tenclass.net ... cost=650
```

### 3.2 内存

| 指标 | r2 | r3 | 说明 |
|---|---|---|---|
| 内部 RAM 空闲 | 120 KB | 104.7 KB | LVGL 缓冲多用 15 KB |
| **内部 RAM 最低水位** | **33.0 KB** | **33.4 KB** | **持平，无风险** |

最低水位是关键指标——它没有下降，说明 15 KB 的增量在运行期被正常回收，
不会引发内存紧张。

### 3.3 稳定性

- 连续运行 **51 分钟**：0 崩溃、0 异常重启
- SD 40 MHz：**0 次读写错误**
- 音频：优先级 2 下 8 轮对话，**0 丢帧、0 解码错误**
- 聊天记录：正常写入，累计 99 条
- 状态流转：idle ↔ listening ↔ speaking 正常

### 3.4 实测感受

界面流畅度较 r2 有明显改善（用户反馈「流畅」）。

## 五、过程中修掉的一个严重 bug

第一版后台化实现**每次开机必崩**（连续 8 次 Guru Meditation），栈回溯：

```
std::char_traits<char>::length(char const*)
Ota::CheckVersion()
Application::CheckNewVersion()
Application::ActivationTask()
```

**根因是 use-after-free**：

```cpp
xEventGroupSetBits(..., ACTIVATION_DONE);  // 主循环收到后 ota_.reset()
CheckNewVersion();                          // 访问已释放的 ota_
```

**修复**：把 `ota_` 所有权 `std::move` 给独立后台任务，主循环侧恒为 `nullptr`，
并给 `HandleActivationDoneEvent()` 里两处读取加判空。

教训：生命周期与并发问题编译期发现不了，必须实机验证。

## 六、明确未做（沿用分析文档结论）

| 项 | 理由 |
|---|---|
| SPI 60 → 80 MHz | 超频会花屏、噪点，随温度漂移 |
| FreeRTOS tick 100 → 1000 | 音频块 32 ms，10 ms tick 已足够 |
| 全屏单缓冲 + full_refresh | 150 KB 全帧拿不到 DMA bounce buffer |
| LVGL 缓冲放 PSRAM | 现方案内部 RAM + DMA 直取更快 |

## 七、已知限制

- 首次开机 / 未激活设备仍需等待版本检查（激活码必须等服务器），此时启动时间
  与 r2 相同
- LVGL 缓冲增大占用 15 KB 内部 RAM；如后续出现内存紧张，把
  `lcd_display.cc` 里的 `width_ * 40` 改回 `width_ * 24` 可省回 15 KB
- LVGL 优先级若再提高（≥3）会导致上行音频丢帧，见 2.4 节实测
